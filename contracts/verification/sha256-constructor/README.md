# Corrected generic-array constructors for SHA-256 research

This profile checks the exact `generic-array 0.14.7` correction preserved in
the [padding profile](../sha256-padding/README.md). The owner selected that
corrected dependency as a research proof target on 2026-10-30.
[Issue #1097](https://github.com/EthereumPhone/PQ1/issues/1097) tracks this work;
the original-dependency correspondence gap remains
[#1067](https://github.com/EthereumPhone/PQ1/issues/1067).
Production Cargo dependencies are unchanged.

The correction writes each generated element through a raw pointer and only
then advances the initialized prefix. Its `ArrayBuilder::drop` destroys only
that prefix. Public `iter_position` and other constructors are outside the
correction. The exact patch, original archive, compiler model and retained
runtime are shared with the padding profile; this batch changes none of them.

## Accepted scope

The symbolic cases retain default, uninitialized-memory, valid-value and
unwinding checks. The two main harnesses use unwind 65:

- U32 and U64 byte defaults return all zero bytes, with the final-byte cover
  reached. The complete output has 313 properties: 300 successful checks,
  12 unreachable checks, and one satisfied cover.
- For every input `[u8; 64]`, the observing generator returns those bytes in
  order and is called exactly once at each index, in increasing order. All
  byte/count/order assertions are reached and successful. There are 265
  properties: 258 successful checks, six unreachable checks and one satisfied
  edge-value cover. This is a contract for this observing generator, not for
  arbitrary closures, element types or array lengths.

Changing the first generated byte fails only the zero-value assertion.
Reversing the generator's index fails only its order assertion. Later checks
or covers made unreachable by those failing assertions are retained explicitly.
Unsupported-operation failures, timeout, build failure or another failed
assertion cannot satisfy either negative control.

A separate paired U1 diagnostic passes for the correction and fails two
initialization checks for the original dependency, at mutable-slice formation
and mutable iteration. Its output assertion and cover still succeed, showing
why checking output bytes alone is insufficient. This is an explicit boundary
of the retained experimental model, not a settled statement about every Rust
validity interpretation. A preceding U32/U64 original-source control exhausted
1,800 active seconds without a complete result; it is preserved as an
incomplete diagnostic and receives no negative-control credit.

Cleanup has **finite** evidence: all 110 complete-or-panicking generator cases
at U0/U1/U8/U32/U64 pass natively and under experimental recursive Miri. These
check generator order and exact initialized-prefix destruction, including every
injected stop index at those sizes. Omitting the first prefix destructor fails
at the intended `initialized-prefix drop mismatch` assertion. This does not
establish universal panic/unwind equivalence or arbitrary destructor behavior.

## Remaining boundary

These constructor results complement the separate padding, initialized
streaming-step and list-level history proofs. They do not compose those results
into complete Rust `Digest` execution, connect the length counter to every
update, or prove the original dependency. Unrestricted slices, callbacks,
alias/provenance semantics, cross-tool correspondence, hardware/accelerated
backends and cryptographic security remain outside the claim.

Two code-generation diagnostics exercised the actual corrected software
callers: a paired one-shot/streaming root and a narrowed one-shot root. Both
compilers received SIGXCPU at the inherited 175-second soft CPU bound before
translation completed. Neither ran a solver or proved a caller property.
The source, command, output and assessment are under `frozen/diagnostics`.
The next complete-caller step needs a bounded translation-cost diagnosis;
these incomplete experiments do not justify changing or suppressing guards.

## Check the recorded evidence

With Python 3.12+, GNU patch and git:

```sh
python3 check.py
python3 test_gate.py -v
python3 inputs.py /absolute/new/constructor-inputs
```

The gate authenticates the parent profile and its production-source/dependency
closure, all frozen inputs, exact historical harness/manifest/lock identities,
recorded tool inventory and complete raw property outputs. Every property
identity, description and status is checked. Historical locations are checked
against the complete saved census; replay permits dependency paths to move
while preserving exact semantic assertion/cover locations in the harness.
Finite cleanup output is checked separately from symbolic evidence.
The CI workflow performs these recorded-evidence checks; **it does not run a
solver or establish new proof evidence**.

`inputs.py` reconstructs the archived packages and exact correction through the
parent preparer, then applies the three declared single-edit controls. Archived
`.rs.in` files are byte-identical source templates, materialized as `.rs` only
in the isolated prepared crates. They are not enrolled in the default Kani
runtime or its production harness census. Input validation independently
reconstructs the files and rejects changed source or extra build scripts;
editing a generated inventory cannot authorize different inputs.

The historical runners authenticated reconstructed dependency files before and
after execution. Their result records pin project files and runtime tools;
the main positive records did not separately serialize the complete dependency
inventory. Frozen runner source and present-day reconstruction preserve that
correspondence boundary rather than inventing a retrospective run inventory.
Recorded output is evidence, not authentication of a historical host or a
proof that Kani/Miri, the private compiler or their memory models are sound.
The parent's source-to-binary and system-library trust boundaries still apply.

## Fresh symbolic replay

Use the retained tool paths described in the parent's
[runtime instructions](../sha256-padding/README.md#fresh-replay-with-the-retained-runtime).
No toolchain is installed or substituted. A newly rebuilt compiler needs its
own evidence and review. The Rustup home embedded in the retained driver must
match the original path.

```sh
python3 run.py \
  --prepared "$CONSTRUCTOR_INPUTS" \
  --kani-root "$CONSTRUCTOR_KANI_TREE" \
  --rustup-home "$CONSTRUCTOR_RUSTUP_HOME" \
  --rustup "$CONSTRUCTOR_RUSTUP_BINARY" \
  --solver-bin "$CONSTRUCTOR_SOLVER_BIN" \
  --compat-libs "$CONSTRUCTOR_COMPAT_LIBS" \
  --case default \
  --output "$CONSTRUCTOR_BUDGET_ROOT/new-default-run" \
  --budget-root "$CONSTRUCTOR_BUDGET_ROOT"
```

Cases are `default`, `generate`, `corrupt-byte`, `reverse-generation`,
`focused-corrected` and `focused-original`. Each output directory is new;
inputs and outputs belong inside the aggregate 6,144 MiB allocation budget.
Run cases serially. Use `--check-only` to authenticate inputs/runtime without
execution, or `--codegen-only` for compilation without proof credit. The main
cases have a 1,800-second active-time bound; focused cases and code generation
have 180 seconds. Linux monotonic time excludes laptop suspension. Raw output
and terminal receipts survive failure.

For finite cleanup reproduction, the two prepared crates are `cleanup-v2` and
`cleanup-wrong-prefix`. Their exact native/Miri commands, tool digests, clean
environments and expected exits are in `frozen/receipts/cleanup-*.json`;
`frozen/runners/run_cleanup_control.py` preserves the historical bounded
runner. Its paths refer to the research workspace and are not a relocatable
entrypoint. The retained Miri sysroot's complete digest inventory is also
preserved. Recursive Miri is experimental. Matching output from different
tools or without that flag is new evidence, not an exact replay of these runs.
