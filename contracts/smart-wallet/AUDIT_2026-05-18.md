## H-1: Factory traps `msg.value` when wallet is already deployed

**Severity:** High (fund loss for retried-deploy calls with attached ETH)
**Location:** `src/PQSmartWalletFactory.sol:75-114`

### What's wrong

```solidity
function createAccount(
    bytes32 masterPkSeed, bytes32 masterPkRoot,
    bytes32 slot0PkSeed, bytes32 slot0PkRoot,
    uint64 chainId, bytes calldata factorySig
) external payable returns (PQSmartWallet account) {
    if (chainId != block.chainid) revert WrongChainId(...);

    bytes32 salt = _salt(masterPkSeed, masterPkRoot);
    address predicted = LibClone.predictDeterministicAddressERC1967(implementation, salt, address(this));

    if (predicted.code.length > 0) {
        return PQSmartWallet(payable(predicted));    // ← msg.value silently dropped
    }
    // ... squat-defence check ...
    (, address deployed) = LibClone.createDeterministicERC1967(msg.value, implementation, salt);
    // ...
}
```

When the wallet is already deployed, the function early-returns without forwarding `msg.value`. The factory has no `receive`/`fallback`, no withdraw, and no admin — any ETH attached is **permanently trapped**.

### Comparison with upstream

Coinbase's factory (`reference/src/CoinbaseSmartWalletFactory.sol:60-69`) does not have this bug. It calls `LibClone.createDeterministicERC1967(msg.value, ...)` **unconditionally**, and Solady's implementation (`lib/solady/src/utils/LibClone.sol`, `createDeterministicERC1967` body, `if iszero(value) { break } ... call(gas(), instance, value, ...)`) forwards `value` to the existing wallet via `call` when `alreadyDeployed`. The PQ early-return path bypasses that forwarding.

### Reproduction

Drop this into `test/AuditH1.t.sol` and `forge test --match-contract AuditH1 -vvv`:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.28;
import {Test} from "forge-std/Test.sol";
import {IEntryPoint} from "account-abstraction/legacy/v06/IEntryPoint06.sol";
import {PQSmartWallet} from "../src/PQSmartWallet.sol";
import {PQSmartWalletFactory} from "../src/PQSmartWalletFactory.sol";
import {MockSPHINCSVerifier} from "./mocks/MockSPHINCSVerifier.sol";

contract AuditH1 is Test {
    function test_factoryTrapETHOnExisting() public {
        MockSPHINCSVerifier c10 = new MockSPHINCSVerifier(); c10.setValid(true);
        PQSmartWallet impl = new PQSmartWallet(IEntryPoint(address(0x4337)), c10);
        PQSmartWalletFactory factory = new PQSmartWalletFactory(address(impl), c10);
        bytes32 sd = bytes32(uint256(0xaaaa) << 240); bytes32 rt = bytes32(uint256(0xbbbb) << 240);
        bytes32 ssd = bytes32(uint256(0xcccc) << 240); bytes32 srt = bytes32(uint256(0xdddd) << 240);
        PQSmartWallet w = factory.createAccount(sd, rt, ssd, srt, uint64(block.chainid), hex"01");

        vm.deal(address(this), 1 ether);
        PQSmartWallet w2 = factory.createAccount{value: 1 ether}(sd, rt, ssd, srt, uint64(block.chainid), hex"01");
        assertEq(address(w), address(w2));
        assertEq(address(w).balance, 0, "wallet did NOT receive ETH");
        assertEq(address(factory).balance, 1 ether, "factory trapped the ETH");
    }
}
```

Expected (failing build): both `assertEq`s show ETH stuck in factory.

### Suggested fix

Prefer **Option 1** (matches Coinbase pattern, smallest diff):

```solidity
function createAccount(
    bytes32 masterPkSeed, bytes32 masterPkRoot,
    bytes32 slot0PkSeed, bytes32 slot0PkRoot,
    uint64 chainId, bytes calldata factorySig
) external payable returns (PQSmartWallet account) {
    if (chainId != block.chainid) revert WrongChainId(uint64(block.chainid), chainId);

    bytes32 salt = _salt(masterPkSeed, masterPkRoot);
    (bool alreadyDeployed, address deployed) =
        LibClone.createDeterministicERC1967(msg.value, implementation, salt);
    account = PQSmartWallet(payable(deployed));

    if (alreadyDeployed) {
        return account;
    }

    // Squat defence: verify bootstrap authorised this slot-0 on this chain.
    bytes32 digest = addSlot0Digest(chainId, slot0PkSeed, slot0PkRoot);
    bool ok;
    try c10Verifier.verify(masterPkSeed, masterPkRoot, digest, factorySig) returns (bool v) {
        ok = v;
    } catch { ok = false; }
    if (!ok) revert InvalidFactorySignature();

    bytes memory bootstrapBytes = abi.encodePacked(masterPkSeed, masterPkRoot);
    bytes memory slot0Bytes     = abi.encodePacked(slot0PkSeed, slot0PkRoot);
    account.initialize(bootstrapBytes, slot0Bytes);
    emit AccountCreated(deployed, masterPkSeed, masterPkRoot, chainId);
}
```

Key change: `createDeterministicERC1967` runs first with `msg.value`. Solady's Yul forwards `value` to the existing wallet automatically when `alreadyDeployed == true`. **Important corner case to test:** when `alreadyDeployed == true`, the squat-defence sig check is skipped — that's deliberate (it was already enforced at first deploy and is unfakeable for a different slot0). Add a test that confirms `alreadyDeployed` returns the same wallet regardless of `factorySig` value.

Add tests:
- `test_createAccount_forwardsValueWhenAlreadyDeployed` — call twice with msg.value, assert wallet balance grew by the value.
- `test_createAccount_alreadyDeployed_ignoresFactorySig` — second call with `c10.setValid(false)` should still succeed.

## H-2: Slot keys can add new owners via `executeWithOffchainCount` self-call

**Severity:** High (bootstrap role-split escape; cap evasion; defense-in-depth breach)
**Location:** `src/PQSmartWallet.sol:172-193, 226-229, 355-360`

### What's wrong

The documented role split (CLAUDE.md §1 and `PQMultiOwnable.sol:50-54`) says **only the bootstrap key (ownerIndex 0) can register new owners**. The on-chain enforcement is partial: `_validateSignature` rejects a slot-signed UserOp whose direct selector is `addOwnerBytes` (`PQSmartWallet.sol:316-319`), but `executeWithOffchainCount(uint256 ownerIndex, uint256 newOffchainCount, address target, uint256 value, bytes data)` accepts an arbitrary `target` and `data`. A slot-1 holder signs:

```solidity
callData = abi.encodeCall(
    executeWithOffchainCount,
    (1, 0, address(thisWallet), 0, abi.encodeCall(addOwnerBytes, (newOwnerPk)))
);
```

On execution:
1. `validateUserOp` — sig `ownerIndex == 1`, selector is `executeWithOffchainCount` (slot-allowed). ✓
2. Counter `slotUses[1] += 1`. ✓
3. EntryPoint calls `wallet.executeWithOffchainCount(1, 0, this, 0, addOwnerBytesCall)`.
4. Inner `target.call{value:0}(data)` → reaches `addOwnerBytes` with `msg.sender == address(this)`.
5. `addOwnerBytes`'s guard `if (msg.sender != address(this)) revert NotFromSelf()` passes.
6. `_addOwner` succeeds. New slot key minted.

### Reproduction

`test/AuditH2.t.sol`:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.28;
import {Test} from "forge-std/Test.sol";
import {IEntryPoint} from "account-abstraction/legacy/v06/IEntryPoint06.sol";
import {UserOperation06} from "account-abstraction/legacy/v06/UserOperation06.sol";
import {PQSmartWallet} from "../src/PQSmartWallet.sol";
import {PQSmartWalletFactory} from "../src/PQSmartWalletFactory.sol";
import {MockSPHINCSVerifier} from "./mocks/MockSPHINCSVerifier.sol";

contract AuditH2 is Test {
    address constant EP = address(0x4337);

    function test_slotCanAddOwnerViaSelfCall() public {
        MockSPHINCSVerifier c10 = new MockSPHINCSVerifier(); c10.setValid(true);
        PQSmartWallet impl = new PQSmartWallet(IEntryPoint(EP), c10);
        PQSmartWalletFactory f = new PQSmartWalletFactory(address(impl), c10);
        PQSmartWallet w = f.createAccount(
            bytes32(uint256(0xaaaa) << 240), bytes32(uint256(0xbbbb) << 240),
            bytes32(uint256(0xcccc) << 240), bytes32(uint256(0xdddd) << 240),
            uint64(block.chainid), hex"01"
        );

        bytes memory attackerNew = abi.encodePacked(
            bytes32(uint256(0x9999) << 240), bytes32(uint256(0x8888) << 240)
        );
        bytes memory innerAddOwnerCall = abi.encodeCall(w.addOwnerBytes, (attackerNew));
        bytes memory wrapperCallData = abi.encodeCall(
            w.executeWithOffchainCount,
            (1, 0, address(w), 0, innerAddOwnerCall)
        );
        bytes memory sig = abi.encode(uint256(1), new bytes(4008));

        UserOperation06 memory op;
        op.sender = address(w); op.callData = wrapperCallData; op.signature = sig;

        vm.prank(EP);
        assertEq(w.validateUserOp(op, bytes32(0), 0), 0);
        vm.prank(EP);
        w.executeWithOffchainCount(1, 0, address(w), 0, innerAddOwnerCall);

        assertEq(w.nextOwnerIndex(), 2, "expected role-split to block slot from adding owners");
    }
}
```

Expected (failing build): `nextOwnerIndex` is **3**, not 2 — the new owner was registered at index 2.

### Impact

1. **Cap evasion.** Slot keys can mint fresh slot keys, each carrying a clean 65,536-sig budget. Total slot-sig budget on a chain becomes unbounded.
2. **Defense-in-depth fail.** If a slot key is compromised, the attacker can install additional slot keys, persisting access even after the user thinks they have rotated.

This is **not** direct fund loss — a slot-key holder already controls the wallet via `executeWithOffchainCount(target=anywhere, value, data)`. But it breaks the documented layered trust model (bootstrap is the only authority that adds signers).

### Suggested fix

Either of:

**Option A (recommended): reject self-target in `executeWithOffchainCount`/`Batch`.**

```solidity
function executeWithOffchainCount(
    uint256 ownerIndex, uint256 newOffchainCount,
    address target, uint256 value, bytes calldata data
) external returns (bytes memory) {
    if (msg.sender != address(_entryPoint)) revert NotFromEntryPoint();
    if (target == address(this)) revert SelfCallForbidden();
    // ... rest unchanged
}

function executeBatchWithOffchainCount(
    uint256 ownerIndex, uint256 newOffchainCount,
    address[] calldata targets, uint256[] calldata values, bytes[] calldata datas
) external {
    if (msg.sender != address(_entryPoint)) revert NotFromEntryPoint();
    // ... existing checks ...
    for (uint256 i; i < n; ++i) {
        if (targets[i] == address(this)) revert SelfCallForbidden();
        // ... existing inner call ...
    }
}
```

Add `error SelfCallForbidden();`. Tests to add:
- `test_executeWithOffchainCount_rejectsSelfTarget`
- `test_executeBatch_rejectsAnySelfTarget` (including mid-array)

**Option B (alternative): drop the role split.** If the design intent is "any owner can add owners" (Coinbase's model), then update CLAUDE.md and `PQMultiOwnable` docstring to match, and remove the `addOwnerBytes` selector check for bootstrap in `_validateSignature`. **Not recommended** — the firmware's Type 1 / Type 2 distinction is built on the bootstrap-only-rotates model.

### Existing tests that must keep passing

- `test_slotCannotCallAddOwner` (already passes the direct-call case)
- `test_bootstrapSignsAddOwner` (already passes the legitimate bootstrap path)
- All other PQSmartWalletTest cases

### Caution

`executeWithOffchainCount` calling other targets that *then* call back into the wallet (e.g., a target contract that calls `wallet.removeOwnerAtIndex(...)`) would `staticcall` fail because `msg.sender == target`, not `address(this)`. So Option A's `target != address(this)` check is sufficient to close the role-split escape — it doesn't need to be transitive.

## H-3: Cross-slot `offchainSigCount` poisoning via mismatched `ownerIndex`

**Severity:** High (1 attacker-sig → 65,536-sig grief on victim slot; future-slot dead-on-arrival)
**Location:** `src/PQSmartWallet.sol:172-193, 287-291`; `src/PQMultiOwnable.sol:220-238`

### What's wrong

`_validateSignature` reads the **signature wrapper's** `ownerIndex` and verifies the C10 sig against that slot's pubkey, then bumps `slotUses[ownerIndex_from_sig]`. `executeWithOffchainCount` reads its **own argument** `ownerIndex` and updates `offchainSigCount[ownerIndex_from_calldata]`. The two are never required to match.

```solidity
// _validateSignature (PQSmartWallet.sol:287-291):
assembly ("memory-safe") {
    ownerIndex := calldataload(sig.offset)   // ← from signature wrapper
    ...
}
// ... verify C10, bump slotUses[ownerIndex] ...

// executeWithOffchainCount (PQSmartWallet.sol:172-185):
function executeWithOffchainCount(
    uint256 ownerIndex,           // ← from callData
    uint256 newOffchainCount,
    address target, uint256 value, bytes calldata data
) external returns (bytes memory) {
    if (msg.sender != address(_entryPoint)) revert NotFromEntryPoint();
    _setOffchainSigCount(
        ownerIndex,                                              // ← uses callData's index
        newOffchainCount,
        _getStorage().slotUses[ownerIndex],
        MAX_SLOT_USES
    );
    // ...
}
```

A slot-1 holder signs:
```solidity
sig wrapper:  ownerIndex = 1
callData:     executeWithOffchainCount(99, 65_000, anywhere, 0, "")
```

Validation: sig OK, `slotUses[1] += 1`. Execution: `_setOffchainSigCount(99, 65000, slotUses[99] /* = 0 */, 65_536)`. Passes (`0 + 65_000 ≤ 65_536`). Storage: `offchainSigCount[99] = 65_000`.

### Reproduction

`test/AuditH3.t.sol`:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity 0.8.28;
import {Test} from "forge-std/Test.sol";
import {IEntryPoint} from "account-abstraction/legacy/v06/IEntryPoint06.sol";
import {UserOperation06} from "account-abstraction/legacy/v06/UserOperation06.sol";
import {PQSmartWallet} from "../src/PQSmartWallet.sol";
import {PQSmartWalletFactory} from "../src/PQSmartWalletFactory.sol";
import {MockSPHINCSVerifier} from "./mocks/MockSPHINCSVerifier.sol";

contract AuditH3 is Test {
    address constant EP = address(0x4337);

    function test_slotPoisonsOtherSlotOffchainCount() public {
        MockSPHINCSVerifier c10 = new MockSPHINCSVerifier(); c10.setValid(true);
        PQSmartWallet impl = new PQSmartWallet(IEntryPoint(EP), c10);
        PQSmartWalletFactory f = new PQSmartWalletFactory(address(impl), c10);
        PQSmartWallet w = f.createAccount(
            bytes32(uint256(0xaaaa) << 240), bytes32(uint256(0xbbbb) << 240),
            bytes32(uint256(0xcccc) << 240), bytes32(uint256(0xdddd) << 240),
            uint64(block.chainid), hex"01"
        );

        bytes memory cd = abi.encodeCall(
            w.executeWithOffchainCount, (99, 65000, address(0xbeef), 0, "")
        );
        bytes memory sig = abi.encode(uint256(1), new bytes(4008));

        UserOperation06 memory op;
        op.sender = address(w); op.callData = cd; op.signature = sig;

        vm.prank(EP);
        assertEq(w.validateUserOp(op, bytes32(0), 0), 0);
        assertEq(w.slotUses(1), 1);

        vm.prank(EP);
        w.executeWithOffchainCount(99, 65000, address(0xbeef), 0, "");

        // Slot 99 is permanently dead-on-arrival when later registered:
        assertEq(w.offchainSigCount(99), 0, "expected sig/calldata index parity");
    }
}
```

Expected (failing build): `offchainSigCount(99) == 65000`.

### Impact

1. **Future-slot poisoning.** Slot 1 can write up to `MAX_SLOT_USES` into `offchainSigCount[N]` for any N. When N is later assigned to a new slot, that slot starts with its combined cap already at-or-near max — dead-on-arrival.
2. **Asymmetric same-slot grief.** Slot 1 can write to `offchainSigCount[2]` and burn slot 2's remaining budget. Cost: 1 attacker sig ↔ ~65,536-sig capacity loss for victim. Combined with H-2, this becomes a way to "exhaust a victim slot then mint a fresh attacker slot to keep going" using the same attacker slot key.
3. **Firmware-bug robustness.** Even without a multi-party threat model, a buggy firmware that mismatches sig vs calldata `ownerIndex` (off-by-one in companion code) silently divergence the on-chain accounting from the firmware's local view. Eventually, slots refuse to sign.

### Suggested fix

Enforce parity using transient storage (Solidity 0.8.24+ has `tstore`/`tload`; the wallet is on 0.8.28).

In `_validateSignature` (`PQSmartWallet.sol`), after sig verify + counter bump:

```solidity
// SPHINCS+C10 sig verified, role split enforced, counter bumped.
assembly ("memory-safe") { tstore(0, add(ownerIndex, 1)) }   // +1 so 0 means "unset"
return SIG_VALIDATION_SUCCESS;
```

In `executeWithOffchainCount` (and `executeBatchWithOffchainCount`), at the top after the entrypoint check:

```solidity
uint256 expectedPlusOne;
assembly ("memory-safe") {
    expectedPlusOne := tload(0)
    tstore(0, 0)                     // consume one-shot
}
if (expectedPlusOne == 0 || expectedPlusOne - 1 != ownerIndex) revert OwnerIndexMismatch();
```

Add `error OwnerIndexMismatch();`. Tests to add:
- `test_executeWithOffchainCount_rejectsMismatchedOwnerIndex` — sig=1, calldata=2, expect revert.
- `test_executeWithOffchainCount_acceptsMatchingOwnerIndex` (regression).
- `test_executeBatchWithOffchainCount_*` symmetric.
- `test_executeWithOffchainCount_failsIfCalledOutsideValidatedFlow` — direct call from entrypoint without prior validate, transient slot 0 is empty, expect revert. (This is also a strong defense — currently anyone with entrypoint impersonation can directly call execute; the transient check requires a paired validate.)

**Implementation note:** transient storage is per-tx, cleared on tx end. The `tstore(0, 0)` consumption inside execute ensures a single validated op can only authorize a single execute (no reuse within the same tx). This is the right shape for EIP-4337's `validateUserOp → executeOp` pairing.

## M-1: Bootstrap budget consumed even if execution reverts

**Severity:** Medium (DoS path; requires bootstrap-level compromise to exploit)
**Location:** `src/PQSmartWallet.sol:338-342`; `src/PQMultiOwnable.sol:199-205`

### What's wrong

`_bumpBootstrapUses` runs inside `_validateSignature`, which is the **validation phase** of EIP-4337 v0.6. Per EntryPoint v0.6 semantics, validation-phase state writes persist even when the **execution phase** reverts (EntryPoint catches execution reverts via `UserOperationRevertReason`).

A bootstrap-signed UserOp with `callData = addOwnerBytes(alreadyRegisteredOwner)` burns 1/65,536 of the bootstrap budget each time it's executed, because:
1. `validateUserOp` passes (selector is `addOwnerBytes`, sig is valid, `bootstrapUses < MAX_BOOTSTRAP_USES`).
2. `_bumpBootstrapUses` runs, persists.
3. EntryPoint calls `wallet.addOwnerBytes(dup)`.
4. `_addOwner` → `_addOwnerAtIndex` reverts with `AlreadyOwner(...)`.
5. EntryPoint catches the revert; validation state stays. Bootstrap budget −1 with nothing to show for it.

65,536 such attempts permanently disable slot rotation for the wallet on the chain.

### Impact

Requires bootstrap-key access. In the firmware's threat model, bootstrap = trust anchor; if it's compromised, many other paths exist. The realistic risk is a **buggy firmware** that retries Type 1 ops with stale state, or a **buggy companion app** that re-submits identical UserOps. Bounded by the trust anchor.

### Suggested fix

Two options:

**Option A: Defer the bump to post-execute.** Restructure so `_bumpBootstrapUses` runs inside `addOwnerBytes` after `_addOwner` succeeds. Keep the `bootstrapUses < cap` *check* in validation (so bundlers see the cap exhaustion early), but defer the actual *bump* to execution. Requires a transient flag.

```solidity
// _validateSignature:
if (ownerIndex == 0) {
    if (selector != this.addOwnerBytes.selector) return SIG_VALIDATION_FAILED;
    if (_getStorage().bootstrapUses >= MAX_BOOTSTRAP_USES) return SIG_VALIDATION_FAILED;
    assembly { tstore(1, 1) }   // mark: pending bootstrap bump
} else { ... }

// addOwnerBytes:
function addOwnerBytes(bytes calldata newOwner) external {
    if (msg.sender != address(this)) revert NotFromSelf();
    _addOwner(newOwner);
    uint256 pending; assembly { pending := tload(1); tstore(1, 0) }
    if (pending == 1) _bumpBootstrapUses(MAX_BOOTSTRAP_USES);
}
```

**Option B: Accept the design, document.** Mark in `PQMultiOwnable.sol` doc-comment that `addOwnerBytes` MUST be called with a non-existing owner, and require the firmware to de-dup pre-sign. Cheaper, but leaves the foot-gun.

Recommendation: **Option A**, coupled with the transient-storage work for H-3 (same mechanism).

## M-2: `assembly ("memory-safe")` annotation in verifier writes FMP and zero slot

**Severity:** Medium (currently latent; a refactor could trigger memory corruption)
**Location:** `src/verifiers/SPHINCsC10Asm.sol:26` (annotation), then writes at `48, 49, 69, 86, 98, 108, 129-130, 154, 166, 186-187`.

### What's wrong

The Yul block is annotated `memory-safe`:

```solidity
assembly ("memory-safe") {
    ...
    mstore(0x40, R)              // line 48 — FMP
    mstore(0x60, message)        // line 49 — zero slot
    mstore(0x40, secretVal)      // line 69
    ...
    mstore(add(0x40, shl(5, i)), mload(add(0x80, shl(5, i))))  // line 108, 166 — overruns into 0x40+...
    ...
}
```

Per Solidity docs, `memory-safe` requires the block:
- Not to use `0x40..0x60` as a writeable scratch area without preserving the FMP,
- Not to corrupt the zero slot at `0x60`,
- Not to write above the FMP without updating it.

The verifier does all three. The compiler can (and does) assume `memory-safe` blocks honor these contracts and may reorder/inline based on those assumptions.

### Why it's not currently exploitable

The function `return(0x00, 0x20)` inside the Yul block, before any Solidity epilogue runs. The downstream code that would read a corrupted FMP simply never executes. The bytecode-freeze test at `test/SPHINCsC10Asm.t.sol:38-39` pins this exact behavior to a specific codehash, catching silent compiler changes.

### Why it should be fixed

A future refactor that:
- Wraps `verify` in additional Solidity logic (e.g., a `view` wrapper that does bookkeeping),
- Inlines `verify` into a caller that allocates memory after the assembly block,
- Or upgrades `solc` past a version where the memory-safety assumption becomes load-bearing,

…would break in hard-to-debug ways.

### Suggested fix

**Option A (smallest diff): drop the annotation.**

```solidity
assembly {
    ...
}
```

The function `return`s from within Yul, so the FMP-not-updated cost is zero (no downstream consumers). Removing `("memory-safe")` is the truthful annotation and removes a latent footgun. Re-run the bytecode-freeze test and update `EXPECTED_RUNTIME_CODEHASH` (which it expects to fail loudly).

**Option B (preserves annotation, slight gas hit): refactor to write above the cached FMP.**

```solidity
assembly ("memory-safe") {
    let base := mload(0x40)         // cache FMP
    // ... use add(base, OFFSET) everywhere instead of literal 0x40, 0x60, 0x80, etc.
    mstore(0x40, add(base, 0x620))  // bump FMP past our scratch region
    // ... do the work ...
    mstore(0x40, base)              // restore FMP before return
    return(...)
}
```

Bigger diff. Probably not worth it given the function returns from within.

Recommendation: **Option A** — drop the annotation, update the codehash, commit message: "verifier: drop misleading memory-safe annotation".

## L-1: `SignatureWrapper` pad bytes not verified

**Severity:** Low (wrapper-keccak malleability; not exploitable for any documented use case)
**Location:** `src/PQSmartWallet.sol:280-295, 408-427`

### What's wrong

The wrapper is `abi.encode(uint256 ownerIndex, bytes innerSig)`:
- `[0..32)`   `ownerIndex`
- `[32..64)`  offset (always 0x40)
- `[64..96)`  inner length (always 4008)
- `[96..4104)` inner C10 sig
- `[4104..4128)` ABI pad (24 bytes, **not authenticated**)

The contract checks `signature.length == 96 + paddedInner` (= 4128), but never reads or constrains bytes `[4104..4128)`. An attacker can flip any of those 24 bytes; the wallet still accepts the signature.

### Impact

- Wrapper `keccak256(signatureWrapper)` is malleable in 2^192 ways.
- C10 sig itself authenticates the digest — **no forgery, no fund loss**.
- Off-chain code that uses `(hash, sig)` as a replay-uniqueness key would be fooled — but EIP-1271 / EIP-4337 callers already shouldn't, and EntryPoint v0.6's nonce protects on-chain ops.

### Suggested fix

Reject non-zero tail bytes in both `_validateSignature` and `_erc1271IsValidSignatureNowCalldata`. Inline:

```solidity
// After the length / offset / innerLen checks, before extracting innerSig:
uint256 tail;
assembly ("memory-safe") {
    // Load the LAST 32 bytes of the signature. The trailing 24 are pad;
    // the top 8 bytes overlap with the last 8 of innerSig (which is authenticated)
    // — so we test against a mask that picks only the 24 pad bytes.
    tail := and(
        calldataload(add(sig.offset, sub(sig.length, 32))),
        0xFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF000000000000
    )
}
if (tail != 0) return SIG_VALIDATION_FAILED;
```

Wait — that mask is wrong; let me recompute. The last 24 bytes are at calldata offset `[sig.offset + 4104 .. sig.offset + 4128)`. Reading `calldataload(sig.offset + 4096)` gives bytes `[sig.offset+4096 .. sig.offset+4128)`. The bottom 24 bytes of THAT word are the pad. Mask: keep the bottom 192 bits, drop the top 64.

```solidity
uint256 tail;
assembly ("memory-safe") {
    tail := and(
        calldataload(add(sig.offset, 4096)),
        0x0000000000000000FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF
    )
}
if (tail != 0) return SIG_VALIDATION_FAILED;
```

Add a test:
- `test_validateUserOp_rejectsNonZeroWrapperPad`
- `test_isValidSignature_rejectsNonZeroWrapperPad`

## L-2: `_erc1271Signer()` returning `address(this)` is a recursion footgun

**Severity:** Low (latent — only fires if a future refactor removes the calldata override)
**Location:** `src/PQSmartWallet.sol:397-399`

### What's wrong

```solidity
function _erc1271Signer() internal view override returns (address) {
    return address(this);
}
```

Solady's `ERC1271._erc1271IsValidSignatureNowCalldata` default body (when not overridden) calls `SignatureCheckerLib.isValidSignatureNowCalldata(_erc1271Signer(), ...)` which `staticcall`s the signer's own `isValidSignature`. If a future refactor removes or shortens `PQSmartWallet._erc1271IsValidSignatureNowCalldata` (lines 401-443) while leaving `_erc1271Signer` returning `address(this)`, the wallet would `staticcall` itself → infinite recursion → OOG.

### Suggested fix

Either add a doc-comment lock:

```solidity
/// @dev DO NOT REMOVE this override or change the calldata override below.
/// `_erc1271Signer()` returning `address(this)` is only safe because
/// `_erc1271IsValidSignatureNowCalldata` is fully overridden and never
/// hits the default body that would `staticcall` ourselves.
function _erc1271Signer() internal view override returns (address) {
    return address(this);
}
```

Or revert to make the dead-path obvious:

```solidity
function _erc1271Signer() internal view override returns (address) {
    revert("unreachable: multi-owner — see _erc1271IsValidSignatureNowCalldata");
}
```

Recommendation: the revert option. If the calldata override is ever accidentally removed, callers hit a loud revert instead of a silent OOG-on-every-call.

## I-2: N-mask layout check lives outside the verifier

**Severity:** Informational (cross-contract coupling; currently adequate)
**Locations:** `src/PQMultiOwnable.sol:244-254` (enforced); `src/verifiers/SPHINCsC10Asm.sol` (not enforced)

The C10 verifier accepts any `pkSeed`/`pkRoot` byte pattern; it relies on the wallet's `_addOwnerAtIndex` to reject non-N-masked layouts (top 16 bytes set, bottom 16 zero) before they reach the verifier via the wallet.

### Why it works today

The verifier is only called by `PQSmartWallet` (and `PQSmartWalletFactory` for squat defence). Both call `c10Verifier.verify(masterPkSeed, masterPkRoot, ...)` where `masterPk*` came from storage written by `_addOwnerAtIndex` (which enforces the N-mask).

### Risk

If a future contract reuses `SPHINCsC10Asm` directly (without going through `PQMultiOwnable`), a non-N-masked pubkey could verify against a sig that the firmware would never produce — leading to byte-divergence between firmware and contract.

### Suggested fix

Pick one:
1. **Document the dependency** in `SPHINCsC10Asm.sol`'s doc-comment: "callers MUST pre-validate pkSeed and pkRoot as N-masked (top 16 bytes, bottom 16 zero)".
2. **Add the check to the verifier** (lightweight): early in `verify`, reject if `pkSeed & ~N_MASK != 0` or `pkRoot & ~N_MASK != 0`.

Option 2 is a few extra opcodes per `verify` and removes the coupling. Recommendation: **Option 2**.

```yul
// near top of verify, after the length check:
if or(
    iszero(eq(and(pkSeed, N_MASK), pkSeed)),
    iszero(eq(and(pkRoot, N_MASK), pkRoot))
) {
    mstore(0x00, 0)
    return(0x00, 0x20)    // return false; never revert here
}
```

## I-3: ERC-6492 dapp-side guidance

**Severity:** Informational (out-of-scope for the wallet contract; companion docs needed)

The wallet inherits Solady's ERC-6492 unwrap, but the **deploy-then-verify simulation** for counterfactual sigs lives on the dapp's side (Solady's `SignatureCheckerLib.isValidERC6492SignatureNow*`, Ambire's `UniversalSigValidator`, viem's `verifyMessage`).

### Concern

A dapp that uses a naive 6492 verifier ("call `factory.create(factoryCalldata)` then `signer.isValidSignature(hash, sig)`") could be fooled by an attacker supplying:
- Arbitrary `factory` address (an attacker contract)
- `factoryCalldata` that deploys a "wallet" at any address the attacker chooses
- A sig that the attacker's "wallet" accepts unconditionally

CREATE2 prevents this only if the dapp checks that the deployed address matches the **predicted** address — but standard 6492 envelopes don't carry the predicted address; the dapp must compute it externally.

### Suggested fix

Add to `docs/companion-app-integration.md` (or a new `docs/erc6492-integration.md`):

> **ERC-6492 verifier requirements.** When verifying a counterfactual PQSmartWallet signature, the dapp MUST check that the signer address it's verifying against equals `PQSmartWalletFactory.getAddress(masterPkSeed, masterPkRoot)` for the user's bootstrap key. Do NOT trust the `factory` field inside the 6492 envelope to determine the signer's identity — that field is attacker-controlled. Use a 6492 verifier that takes the signer address as an explicit input (Solady's `isValidERC6492SignatureNow`, viem's `verifyMessage`) and rejects any envelope whose factory call produces a different address.

No contract change needed. Just docs.
