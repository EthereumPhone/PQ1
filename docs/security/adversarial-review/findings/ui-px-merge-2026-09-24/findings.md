## FINDING 2 — the NS glyph atlas is safe only by an undocumented, unenforced assumption

Commit e56d533e moves the 75,128-byte glyph atlas out of the secure slot
into NON-SECURE flash (`nonsecure/assets/ui-px/atlas.pq1a`, at
`NS_FLASH_BASE + 0x1000`). The secure world keeps only its SHA-256
(`ATLAS_ROOT`) and re-hashes:
* `verify_atlas()` before a pixel dialog,
* `atlas_root_proof()` after it, at 12 sign-handler sites, refusing to
  release a signature unless it is `OK_SENTINEL` again.

The design is deliberate and well documented, and it is fail-closed
against a persistent swap. BUT `Atlas<'a> { data: &'a [u8] }` BORROWS —
glyphs are read live from NS flash during the paint, never copied into
S-SRAM. So the residual attack is swap-during-dialog-then-restore:
NS reprograms a glyph page after the pre-check, the user reads a wrong
digit, NS restores the original bytes, the post-check passes, the
signature is released.

**Not reachable today.** Verified on primary source:
* `ITNS` is never written anywhere in the repo => NVIC_ITNS stays at its
  reset value, i.e. every interrupt is SECURE on ARMv8-M;
* `nonsecure/src/` declares no `#[interrupt]`/`#[exception]` handler at
  all — NS is a pure polling loop (`device.poll`, `poll_tx`);
* NS reaches the secure world only through synchronous NSC calls, so
  while a dialog is open NS is blocked inside that call, not executing.

So NS currently has no way to run concurrently and cannot reprogram flash
mid-dialog. The trusted display's integrity therefore rests on
"NS never executes asynchronously" — an invariant that is:
* nowhere stated in `assets.rs` or the port plan,
* nowhere enforced (no const assert, no boot check, no test),
* and silently broken the day anyone gives NS an interrupt (moving USB
  from polling to interrupt-driven is the obvious trigger).

Cheap fix: assert `NVIC_ITNS == 0` at boot and/or before each pixel
dialog, and record the coupling at both sites.

Note: splitting "font to secure flash, marks to NS" does NOT help — the
font is 68,867 of the 75,128 bytes (92%). The WYSIWYS-critical part IS
the bulk, which is exactly why it was moved.

### [HIGH] assets::atlas() renders from NS flash with NO root check after the first call — the verdict is cached, the bytes are not
* `secure/src/ui/px/assets.rs:133-147 (BOOT_OK arm at :135)`  — dim `ns-atlas`, confirmed-in-source, refuted by 0/2
* **Broken:** `atlas()` caches only the *verdict* (`BOOT_STATE`), never the bytes. On every call after the first it does `BOOT_OK => Atlas::parse(window())` — re-reading live non-secure flash at 0x0810_1000 — with no `atlas_root_proof()` and no `ATLAS_ROOT` comparison. Nothing ever demotes `BOOT_STATE` back to `BOOT_BAD`: `verify_atlas()` (:109) writes `BOOT_STATE` nowhere, so a later hash failure leaves the cached `BOOT_OK` in place forever. Consumers of this unverified view are `lcd.rs:417 paint_legacy`, `:521 film_start_with`, `:555 film_tick`, `:569 film_resolve`, `:622 show_busy`, and `screens.rs:167 progress_film`. `paint_legacy` is reached from EVERY legacy 16x4 page, because `secure/src/ui/lcd.rs:154-160` now makes `Display::flush()` call `crate::ui::px::lcd::paint_legacy(&self.rows)` and `return` when it succeeds — so the secure-resident glyph blitter is skipped. `ui/confirm.rs:239-255` (`confirm_checked_inner`) draws and flushes through exactly that `Display`. The module doc at assets.rs:17-20 claims the non-dialog painters use "a once-verified cached view", and nsc/mod.rs:1136-1139 claims the legacy fallback's "glyphs are secure-resident". Both are false in the tampered state.
* **Scenario:** Threat model is a fully compromised NS world (invariant #4). Bank 2 is entirely non-secure (Makefile:274-275 and every flash recipe: `SECWM2_PSTRT=0x7F SECWM2_PEND=0x0`, i.e. an EMPTY secure watermark on bank 2), no WRP is programmed on bank 2 in any shipping recipe, and FLASH_NSCR is in the NS alias of the FLASH register block (secure/src/hw/flash.rs:40-45,1126 — the secure world itself must use the NS alias to program bank-2 pages, which is only true because those pages are NS). So NS can erase and reprogram its own slot, including the atlas window, at runtime. Attack: (1) at boot, before NS runs, some legacy flush sets BOOT_STATE=BOOT_OK; (2) NS then blanks the 4-bit-alpha bitmap of the '0' glyph — this needs only 1->0 bit programming, no erase; (3) NS calls CMD_OFFCHAIN_SYNC with a large target. cmd_offchain_sync.rs:155-172: `px_confirm_plain(...).ok()` -> `verify_atlas()` fails (hash no longer matches) -> `Err` -> `.ok()` = `None` -> `confirm_checked(pages.as_slice())` -> `Display::flush` -> `paint_legacy` -> `atlas()` -> BOOT_OK -> renders with the tampered font. The pages carry `current_count` / `target_count_for_display`; "1000" renders as "1". The user approves what reads as a +1 counter nudge and actually authorises a +1000 raise of the monotonic off-chain floor, burning the slot's few-time budget toward the invariant-#7/#9 combined cap. The identical fallback exists for the firmware-update consent (fw_update/mod.rs:60 -> :77, and :150-170 -> the `confirm_checked(&pages)` showing the version, rollback floor and the two 8-word fingerprints) and for the receive-address consent (cmd_get_wallet_address.rs:402 -> :407). In each case the post-confirm `atlas_root_proof()` re-check is skipped, because every one of those re-checks is gated on `if px_route` / only runs inside `px_confirm*`.
* **Fix:** Two one-liners, either of which closes it: (a) make `atlas()` call `atlas_root_proof()` on every call instead of trusting `BOOT_STATE` (it is already `hash_flash` over 75 KB, ~ms, and these are not per-frame paths except `film_tick`, which can keep a cached verdict only if it also re-hashes); or (b) at minimum, have `verify_atlas()` store `BOOT_BAD` on failure so one failed dialog permanently demotes the legacy painter to the secure-resident glyph blitter. (a) is the correct fix; (b) alone still leaves the window between the swap and the first `verify_atlas()` call.

### [HIGH] Glyph data is read LIVE from non-secure flash on every frame; the pinned root is checked before and after the dialog, never at use
* `secure/src/ui/px/assets.rs:55-64 (window), 71-92 (AtlasRef::font/marks), lcd.rs:725-726`  — dim `ns-atlas`, suspected, refuted by 0/2
* **Broken:** `window()` hands out a `&'static [u8]` over NS flash (`NS_FLASH_BASE + 0x1000`, ATLAS_LEN = 75128). `AtlasRef::font()` / `marks()` return `Font<'static>` / `Marks<'static>` that are just borrowed sub-slices of that window — nothing is ever copied into secure SRAM or secure flash. `lcd.rs:725-726` binds `marks`/`font` once per flow and `render_strip` dereferences those NS-flash slices for every glyph of every strip of every frame, for the whole duration of the confirm dialog. The verification is therefore check-then-live-read, not check-at-use. The mitigation is a re-hash after the dialog (nsc/mod.rs:1122, :1164, cmd_sign_userop.rs:1489, :1944, cmd_sign_userop_batch.rs:900/1676/2105, cmd_sign_offchain.rs:799/1155). A check-after cannot detect a swap that is restored before it runs, so the comment at assets.rs:15-18 — 'a glyph swap during the dialog is a refusal, never a release' — is false as written, independently of whether the race is reachable. Marking `suspected` only because reachability depends on two things I could not settle from this repo: (1) whether the STM32U585 implements a banked NS SysTick (ARMv8-M SysTick is a banked system exception, NOT governed by NVIC_ITNS, and a compromised NS can arm it via the NS alias at 0xE000E010); (2) NS bus-master closure. On (1): NVIC_ITNS is never written anywhere in the tree (no writes to 0xE000_E380), so NS external IRQs are all Secure-targeted; AIRCR.PRIS is set (sau.rs:648,702), but PRIS only maps NS priorities into 0x80..0xFF, which still preempt secure THREAD-mode code, and the pixel flow masks nothing — `cortex_m::interrupt::free` appears only in flash.rs / otp.rs / iwdg.rs / uart_log.rs / shio.rs, never in the px dialog (it cannot, since run_flow depends on the secure 1 kHz SysTick). On (2): this repo's own docs/security/a-b-firmware-rollback-architecture.md:3904 lists 'GPDMA1: arbitrary-address AHB master with reset-default nonsecure channels' and :3915 explicitly refuses to call master closure proven; no code anywhere configures GPDMA_SECCFGR.
* **Scenario:** NS sets up a concurrent writer (NS SysTick handler, or an NS-owned GPDMA1/DMA2D/SDMMC-IDMA channel armed before the NSC call), then calls CMD_SIGN_USEROP. `verify_atlas()` hashes the window and passes. During the dialog — while the user is paging through the address/amount screens — the writer blanks the '0' glyph bitmap (1->0 programming only, no erase needed, 16 B per quad-word). The user reads '2 USDC to 0xAAAA' where the transcript actually says '200 USDC'. Before the user presses the two-button chord, the writer restores the original bytes (an 8 KB page erase plus reprogram, or simply keeping a pre-erased spare page and re-pointing — timing is entirely under the attacker's control because the human is the slow element). Both `atlas_root_proof()` re-checks then pass, `cr_verdict == OK_SENTINEL`, and the signature is released over the transaction the user did NOT read. This defeats 'no blind-sign path for known shapes' and invariant #4 while every FI sentinel and every transcript proof reports green. Note the same race also splits `verify_atlas()` itself: it hashes at :111 and then RE-READS the same flash at :115 (`Atlas::parse(window())`) and :116-117 (`Font::parse`), so even the structural validation is performed on bytes that were not the hashed ones.
* **Fix:** Copy the verified bytes out of NS flash before use. The atlas is 75 KB and secure SRAM cannot hold it, so the realistic fix is either (a) hash-per-frame (hash the window inside the frame loop, refuse the flow on mismatch — `hash_flash` over 75 KB at 160 MHz with the HW HASH block is well inside the 16 ms frame budget only if measured, so measure it), or (b) copy just the tiers actually used by the live transcript into the existing secure BSS after the hash, and render only from that copy. Independently, and regardless of the race: fix the false comment at assets.rs:15-18 and record the NS-SysTick / GPDMA non-preemption premise as an explicit, tested security assumption (it is currently load-bearing and unstated).

### [HIGH] Pixel UI removes the WYSIWYS scroll-to-end gate: the opening hero is commit-armed, so a signature can be released before any detail screen is displayed
* `secure/src/ui/px/confirm_px.rs:36 (also px/lcd.rs:759, pqsigner-ui-px/src/driver.rs:151)`  — dim `sign-handlers`, confirmed-in-source, refuted by 0/2
* **Broken:** `pub const PX_COMMIT_REQUIRES_SEEN_LAST: bool = false;` disables the 2026-06-26 scroll-to-end gate on the pixel path. `FlowDriver::armed()` returns `sign: s.kind().is_some_and(Kind::may_commit) && s.commit()`, `Kind::may_commit` is `Hero | Confirm` (screen.rs:190-192), and `px_lift::structure_ok` REQUIRES the opening screen to be a commit-armed hero (px_lift.rs:331-334: `if hero.kind() != Some(Kind::Hero) || !hero.commit() { return false; }`). `FlowDriver::new` starts at `cur = 0` (driver.rs:87-92). So on every pixel sign dialog the very first screen shown is sign-armed, and `run_flow`'s `sign_ok = armed.sign && (!PX_COMMIT_REQUIRES_SEEN_LAST || driver.seen_last())` collapses to `armed.sign`. The legacy path it replaces demotes a premature confirm to 'advance one page' (confirm_core.rs:65-72). The hero carries no security-critical fields: for a plain transfer it is `SEND 0.250000 ETH?` with no recipient/chain/fee (value_transfer_screens.rs:57-70), for a contract call literally `CONFIRM CONTRACT CALL?` (line 59), and for the blind route `CONFIRM UNKNOWN CALL?` (blind_sign_screens.rs:5-8). TO, VALUE, MAX FEE, NONCE LANE and the ERC-8213 fingerprint are all downstream detail/trailer screens the user never has to reach.
* **Scenario:** A hostile companion submits a drain UserOp (`transfer(attacker, all)` to an unknown contract). The device opens on `CONFIRM UNKNOWN CALL?` with the sign gesture already armed. The user presses both buttons — the same gesture that has always meant 'confirm' on this hardware (hw/buttons.rs:297-299 synthesises the two-button chord as the confirm event) — and releases. The signature is released without the target address, the value, the calldata hash or the fingerprint ever having been on the glass. On the legacy 16x4 path the identical physical chord advanced one page instead, because `NavigationCore::handle(RightLong)` requires `seen_last` (confirm_core.rs:66-72).
* **Fix:** Set `PX_COMMIT_REQUIRES_SEEN_LAST = true` in secure/src/ui/px/confirm_px.rs:36 (both loops already maintain `seen_last`, so no other change is needed), or arm sign only on the returning hero / `Confirm?` and never on screen 0.

### [HIGH] A two-button chord already held when a pixel dialog opens is replayed as a fresh chord and signs on release — no dialog-boundary release gate
* `secure/src/ui/px/lcd.rs:727-734 (with pqsigner-ui-px/src/input.rs:249-285, 306-319)`  — dim `sign-handlers`, confirmed-in-source, refuted by 0/2
* **Broken:** `run_flow` constructs `InputFsm::new(InputCtx::NAV)` with both sides `down: false` (input.rs:136-163) while `sampling_enable()` seeds `STABLE_BITS` from the LIVE pin levels (`STABLE_BITS.store(read_bits(), ...)`, lcd.rs:157). The first `drain()` therefore polls the FSM with whatever is physically down and synthesises new edges: with both buttons down it emits `Press(Left)` then, on the second side, `Chord` with `chord_overlap = true` (input.rs:261-284). Releasing both then emits `ChordClick` (input.rs:312-318), which `run_flow` maps to `NavGesture::Chord` -> `NavResult::Sign` on the commit-armed opening hero (lcd.rs:797-808). Nothing between two consecutive dialogs waits for the buttons to come up: `show_ending` is just `film_resolve` (lcd.rs:436-438), a fixed animation loop with no input handling, and the batch handler paints it and goes straight into the next member's dialog (cmd_sign_userop_batch.rs:1698-1708). This composition is NOT covered by the documented residual in HARDENING.md 2.4, which describes 'a squeeze on a commit-armed screen' — here the squeeze begins before the screen exists. Under the legacy gate the same straddling chord was harmless (demoted to page-advance).
* **Scenario:** Atomic batch of 3 UserOps. The user reads member 1 fully, squeezes both buttons to confirm. The device paints the `TX 1 OF 3 CONFIRMED` ending film and immediately opens member 2's dialog. The user, expecting the same gesture, squeezes again during or right at the end of the ~1-2 s film; that squeeze is live when `run_flow` for member 2 calls `sampling_enable()`, so it is replayed as `Press` + `Chord`, and the release emits `ChordClick` on member 2's opening hero — member 2 is confirmed without a single one of its detail or trailer screens being displayed. The same shape occurs single-shot: a hostile companion queues a drain `SIGN_USEROP` immediately after a benign one, or the user hold-left-declines a request (left is still physically down when `HoldCommit(Left)` fires and `run_flow` returns) and then adds the right button on the dialog the companion re-opens.

Flipping `PX_COMMIT_REQUIRES_SEEN_LAST` also neutralises it.

### [HIGH] Scroll-to-end consent gate is OFF on every pixel sign dialog: the opening ask is commit-armed, so one chord click signs without any detail screen ever being displayed
* `secure/src/ui/px/confirm_px.rs:36 (const), 118 (use); secure/src/ui/px/lcd.rs:759 (hardware path)`  — dim `clear-signing`, confirmed-in-source, refuted by 0/2
* **Broken:** The legacy 16x4 dialog enforces a WYSIWYS scroll-to-end gate (secure/src/ui/confirm.rs:141-159, commit ccfa5f61, audit 2026-06-26): the confirm gesture is demoted to 'advance one page' until the LAST page has been displayed at least once, and the flag is an FI-hardened FihBool inside NavigationCore. The two-button chord click there returns NavResult::Sign and mints OK_SENTINEL immediately. Nothing forces the refund / native-value / gas-lane / ERC-8213 fingerprint / multiSend-record screens to be shown before the signature is released. Secondarily, FlowDriver.seen_last (pqsigner-ui-px/src/driver.rs:76) is a plain `bool`, i.e. flipping the const back to true would restore the policy but NOT the F14/SCAFI-2 FI hardening the legacy path has.
* **Scenario:** A hostile or merely careless companion sends a SafeTx whose inner call reads benignly but which also carries gasPrice/gasToken/refundReceiver set to drain the Safe's full USDC balance 'as gas', or a non-zero safeTxGas that makes the inner call silently no-op. This is verbatim the failure the 2026-06-26 audit closed on the legacy path ('a user could long-press on page 0 and authorise a signature without ever seeing the security-critical pages the dispatcher splices in ... defeating every per-page WYSIWYS mitigation in the firmware'). If the design's arming is to be kept instead, that decision needs to be re-ratified by the owner in this repo's own record rather than in the incoming branch's HARDENING.md edit.
