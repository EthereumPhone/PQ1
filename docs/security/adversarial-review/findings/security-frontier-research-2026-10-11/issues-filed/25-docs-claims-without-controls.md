TITLE: Docs and comments that describe controls or states the code does not have (ten items, 2026-10 frontier research)
LABELS: documentation,finding,priority:low,surface:docs,source:frontier-research-2026-10
---
Ten statements in checked-in documents or comments that a reviewer would take at face value and that do not match the code. None has a tracking issue. Each is a one-line fix or a decision; tick them off as they are corrected.

Line numbers at master `0feea78a` (2026-10-11). The research ran at `c75b0d9c`, an ancestor of master; the cited files were diffed against master before filing.

- [ ] **Boot-time SE attestation.** `docs/security/HARDENING.md:32` (residency table) and the lifecycle line in `CLAUDE.md:57` ("SE attest") read as present fact. No attestation read exists in `secure/src` (a search for "attest" finds two comments). `docs/security/threat-model.md:505` correctly says "Boot-time SE attestation is not yet landed". The rest of HARDENING.md section is written as requirements, which is fine. Work itself: #210, #249.
- [ ] **PIN credential design that does not exist.** `docs/security/HARDENING.md:30-31`, `:158-163` ("Type: AESKey (not UserID — UserID is plaintext on the I2C bus)") and `:258-270` ("NS UI collects PIN digits, passes a byte buffer into a Secure NSC entry point"). The code uses an SE050 UserID object, has no PIN stretching, and collects the PIN in the secure world.
- [ ] **Consumption mask "keeps the signature uncorrelated".** `secure/src/nsc/mod.rs:699-701`. Neither board drives a load from the mask pin, and the `compile_error` text a few lines below (`:714-726`) already says the effect is not established. Also: `docs/security/red-teaming.md:694` says the duty PRNG is "seeded from `rng_strong`" while the driver deliberately forbids that (`secure/src/hw/consumption_mask.rs:150-156`, `:188-190`), and `README.md:88` says the hooks are "All feature-gated; CI keeps them out of production" while the mask is production-required. Measurement itself: #228, #646.
- [ ] **`NsPtr` typestate named as the pointer-validation mechanism.** `docs/security/threat-model.md:263`. `NsPtr` has one production use (`secure/src/nsc/mod.rs:2032`); twelve handler files call the boolean `validate_ns_*_ptr` functions directly, and `secure/src/nsc/ns_ptr.rs:27-34` says the migration is pending. Pointers are validated; the mechanism name is wrong. Adoption: #84.
- [ ] **Tamper docs stale in both directions.** `docs/hardware/hardware_requirements.md:100-103` says the TAMP driver is "currently log-only and not yet wired into `main()`"; it is called at `secure/src/main.rs:1403` and escalates under `tamp-wipe` (`secure/src/hw/tamp.rs:103-109`). The comment at `secure/src/main.rs:1396-1400` ("Log-only; never halts and never wipes"), the log strings at `:1405-1407`, `:4348-4350` and `secure/src/hw/tamp.rs:78-81` are false under `tamp-wipe`. The same doc says the hardware key is erased in hardware on any tamper, which is true only for the runtime copy: the wrapped key is reloaded from flash page 126 each boot.
- [ ] **"No NRST needed (vector catch)".** `docs/security/user-device-verification.md:184-186` (argued at `:72-80`). The document argues the pre-attach window is harmless. It contradicts invariant 10(a) ("connect-under-reset, before first power") and the verifier's own default (`tools/verify_ship_state.py:112-115`, `--mode UR`, which needs NRST). One of the three must change (see {{06}}).
- [ ] **"No hardware measurement latch on STM32U585".** `docs/security/vendor-signing-key-compromise.md:459-463`. Literally true (there is no measurement register), but the reason given does not cover an immutable first stage that derives a value and then closes HDP, and HDP access-disable is a deny-until-reset latch (RM0456 section 7.5.3). The document's conclusion stands; the reasoning is imprecise. Editorial.
- [ ] **FSBL sources argue against their own default.** `fsbl/src/verify.rs:5-24` and `fsbl/src/main.rs:40-47` say the HASH-peripheral port "is no longer worth its cost"; `fsbl/Cargo.toml:16` has `default = ["hw-sha256"]`. `CLAUDE.md` invariant 10 and `fsbl/memory-stm32u585.x:14` quote 28,704 B; the pq1 FSBL built on 2026-09-28 is 22,236 B (commit `c6a97080`, "30,720 -> 22,236 B"). The 2.93 s boot-work figure is the software-hash measurement.
- [ ] **Mask and bench docs stale.** `docs/hardware/evt-silicon-validation.md:757-765` says a `mode-production` pq1 image is unsatisfiable because the mask is TIM2_CH1 on PA5; the mask moved to TIM3_CH1 / PA6 (`secure/src/board/pq1.rs:319-336`). Several files point to "§9" of that document for the open load measurement, and §9 never mentions the mask. `:921-923` says power analysis needs a ChipWhisperer that is not on the bench; `docs/security/red-teaming.md:97-105` assigns it to the oscilloscope with a shunt. `docs/hardware/hardware_requirements.md:119-122` lists the mask as optional on PA5 while the production fence makes it mandatory.
- [ ] **`wait_random` listed as "Planned".** `docs/security/threat-model.md:321`. It is implemented (`secure/src/fi.rs:76-95`) and called from over 200 code lines. This one is an under-claim.

Evidence level: document against code, re-checked independently at `c75b0d9c`. Two corrections to the research report came out of that re-check and are applied above: the threat model's "18 gateway commands" count is correct for the ship set and is not listed, and the HARDENING.md attestation text is mostly a requirements statement.

Doc drift that already has an owner is not repeated here: Shielded Connection freshness (#117), "CI-pinned" geometry (#720), PIN echo and progressive delay (#637), SRAM ECC "always active" (#48), `verify-repro` on every PR (#456), the duress wipe-list claim (#107).
