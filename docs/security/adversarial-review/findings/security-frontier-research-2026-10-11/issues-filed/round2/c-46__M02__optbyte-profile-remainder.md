**What is still unowned in the ship option-byte profile (2026-10-11 security frontier research, item M02; follows yesterday's comment on the OEM-lock bits).**

Already tracked, so not repeated here: the OEM-lock bit positions (yesterday's comment), SRAM_RST (#848), the inert RDP-2 burn (#849), the log-only boot-address verdict (#856), the bootloader tripwire (#270), the per-unit factory record (#595), the BOOT_LOCK order (#753), the slot tail (#864). Re-reading the profile code at master, six things are left that none of those asks for. All six decide what gets frozen when the first unit locks itself.

1. **The exact OPTR compare was closed without being implemented.** #141 carried it ("SL9: Phase-A ship-profile check is a partial OPTR mask; make it an exact masked compare"). The closing commit `54e3ba84` only added a note. At master `shared/src/lockdown.rs:375` still says "this is deliberately a PARTIAL mask", and `optr_matches_ship` (`shared/src/lockdown.rs:381`) checks three things: TZEN, the RDP byte and SWAP_BANK. Every other OPTR bit is carried into the permanent state unchecked: the brown-out level, nSWBOOT0 / nBOOT0, the watchdog bits (#248) and the four SRAM bits (#848 is one instance of this gap). This issue is now the only open owner of the general fix.
2. **The brown-out level is decoded but never checked.** `shared/src/lockdown.rs:521` defines `bor_lev`; the comment at `shared/src/lockdown.rs:518` says "not yet a hard gate". `verify_ship_profile` (`shared/src/lockdown.rs:534`) never calls it. The ST production value has the level at 0 (see #848).
3. **A comment in the same file contradicts the file and the manual.** `shared/src/lockdown.rs:559` says a clear BOOT_LOCK leaves "SECBOOTADD0 and SWAP_BANK mutable at RDP-2". `shared/src/lockdown.rs:388` says, correctly, that the manual excepts only SWAP_BANK. RM0456 Rev 7 section 7.6.2, Level 2: "Option bytes cannot be programmed nor erased except the SWAP_BANK option bit." So after the lock BOOT_LOCK matters for SWAP_BANK only; before the lock it protects the boot address. #753 and #856 lean on this, so fix the comment in the pin commit.
4. **The factory text still names bank 1 and pages 0 to 3.** `docs/provisioning/first-boot-provisioning.md:48` tells the factory to set "WRP1A" on the bootloader pages, and the next line says pages 0 to 3. Phase A requires pages 0 to 4 in both banks (`shared/src/lockdown.rs:564`, `shared/src/lockdown.rs:572`). A factory that follows the text produces units that halt at Phase A. That fails closed, but the text is the instruction the pinned values will be copied from.
5. **Facts the factory OEM-key step and its read-back need.** `docs/provisioning/first-boot-provisioning.md:49` gives "OEM-key finalization" to the factory with no procedure. From RM0456 Rev 7 (section 7.6.2, "OEM1/OEM2 lock activation", and section 7.9.7): each key is 64 bits in two registers, so there are four registers to write (they are already listed in this issue's body). The status bits say the key "read during the OBL is not virgin", so a lock bit changes only after an option-byte reload or a power cycle; a read taken straight after the write proves nothing. The manual also notes that a key "must not contain only 1 or only 0". Whether writing all ones at RDP-0 returns a planted key to virgin is not stated outright and is not confirmed on silicon. One correction that follows: the fourth fix bullet of #849 ("Overwrite the OEM1 and OEM2 keys in the same ceremony") cannot mean the on-device burn. Requirement R2.1 says "The flow MUST NOT program WRP or any option" byte other than RDP (`docs/provisioning/first-boot-requirements.md:46`), and `fsbl/src/optbytes.rs:13` cites the same rule. Phase A reads the lock bits and halts; the key write is the factory's.
6. **Two open issues ask for opposite OEM2 postures.** #40 (open, labelled ship-blocker) asks to provision a secret OEM2 key so that a gated debug reopen exists after the lock. `shared/src/lockdown.rs:264` and #387 (A4b) require that a shipped unit has no OEM key at all. Phase A's OEM gate, the factory clear step and the user-side read of bits 18 / 19 are all built on the second position. This is an owner decision. Until #40 is closed or reworded, pinning the OEM mask pins a rule that another ship-blocker contradicts.

Suggested additions to this issue's checklist:

- [ ] Give `ShipProfile` an expected OPTR value and a don't-care mask, compare the whole register in `optr_matches_ship`, and host-test both directions. Fold SRAM_RST (#848) and the brown-out level in as fields of that one compare. Firmware and host tests; the values come from the bench read below.
- [ ] Decide the shipped brown-out level (#49, #248) and make it a checked field.
- [ ] Correct the comment at `shared/src/lockdown.rs:559`, and the page range and bank list in `docs/provisioning/first-boot-provisioning.md:48`. That text is mirrored in two other documents (`docs/provisioning/first-boot-provisioning.md:41` names them; the next line says to change all three).
- [ ] Reword the fourth fix bullet of #849 so that the OEM key write is a factory step.
- [ ] Write the factory OEM step down: write all four key registers, reload option bytes or power-cycle, then read FLASH_NSSR bits 18 / 19 and record them per unit (#595).
- [ ] Bench, on a board with a debug port that may be left keyed if the clear fails: at RDP-0 provision an OEM2 key, reload, confirm bit 19 sets and the corrected predicate trips; write all ones to the four registers, reload, confirm both bits clear.
- [ ] Owner: resolve #40 against the no-OEM-key rule before `OEM_LOCK_MASK_PINNED` is flipped.

One untested lead for the same bench work: section 7.6.2 says that at Level 2 debug is "definitively disabled" if no OEM2 key was provided, and stays enabled under reset (for the authentication registers only) if one was. If that holds on this part, "does the unit still answer on the debug port under reset after it locked itself" is an outside check for a planted OEM2 key that needs no firmware. It needs a sacrificial unit at RDP-2.

**All of this has to be settled before the first unit runs the self-lock, because RDP-2 freezes whatever the option bytes hold.** No board change is needed. The reviewer's own caution applies: every on-device check runs in flash that a transit attacker at RDP-0 can rewrite, so the per-unit factory record (#595) and the buyer-side read (#850) stay the load-bearing controls; the on-device checks only stop an attacker who changes option bytes and leaves flash genuine.
