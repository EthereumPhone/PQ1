**Design corrections to this issue's checklist, from the 2026-10-11 security frontier research (the "birth record" part of its item on verifying a unit before first power).** The UID address already has its own comment above and is not repeated. Lines are at master `c2fab970`.

The research kept the substance of this issue (a signed per-unit record of the three chip identifiers, in a public log) and changed where and how it is checked. Seven points, each against a box in the body:

1. **Verify on the host, not on the device.** The boxes "SE050 attestation at boot", "OPTIGA attestation at boot" and "Boot-time ceremony ... Any mismatch → permanent lockdown" make the secure world verify two vendor ECDSA certificate chains and an SLH-DSA-128s signature. That puts a classical verifier and a second post-quantum verifier into firmware. Invariant 5 (`CLAUDE.md:26`) names one exception for classical signature checking, the host-only catalogue tool, fenced by `make classical-crypto-boundary`. A device checking itself also tells a buyer nothing if the unit was swapped or reflashed in transit, and a lockdown on mismatch is a new way to brick a unit. The research recommends that firmware only reads and relays (the two secure-element identifiers, the vendor certificate, a signature over a host challenge) and that the host tool and the companion do all the verifying.
2. **Bind each proof to its own root, and test the negative.** The host must verify each chip's proof against that vendor's root only, and require the identifier tuple to be identical in both proofs, in the manifest and in the log entry. Add a test in which a valid OPTIGA proof is presented in the SE050 position and must fail. Trezor published a fix in 2026 for a device-authentication check where one proof could satisfy every chain ([advisory](https://trezor.io/vulnerability/authenticity-proofs-not-bounded-to-their-secure-element), cited by the research; I did not re-fetch it).
3. **The "DHUK probe via SAES against factory-recorded value" box cannot be done.** The first paragraph of this issue already says why: the factory never runs at a lock level where the per-die key exists. The box should be removed.
4. **The storage boxes collide with existing rules.** "Manifest stored 3×: ... STM32 internal flash" conflicts with the first-boot check that the per-device flash pages are blank (`secure/src/first_boot/mod.rs:201`; the error is `PerDevicePageNotBlank`, `secure/src/first_boot/state.rs:83`), and every other flash page already has exactly one owner in the geometry registry (`geometry/src/lib.rs:274`). "SHA3-256 anchor to STM32 OTP bytes 6-37" lands inside the region the code marks as the unsupported legacy rollback tally (`secure/src/hw/otp.rs:29`). Any hash that covers one-time-programmable memory must leave out bytes 128 to 160, which hold the device master secret (`secure/src/hw/otp.rs:30`); the research had first proposed hashing the whole area and withdrew that.
5. **SHA-256 or SHA3-256.** `firmware_hash` and `device_serial` are specified with SHA3-256. Everything else in the project hashes with SHA-256 (Keccak only where the EVM requires it), and the firmware measurement a buyer compares is a SHA-256. The research recommends SHA-256 here so the manifest does not bring in a second hash family. If SHA3 stays, it should be a recorded choice.
6. **Identifiers are a privacy surface.** Secure-element identifiers, the vendor certificate and a challenge signature that any host can request before unlock are a stable device identifier for every web page that can open the USB device. A public log of identifier tuples is one too. Either gate the readers (first boot only, or after unlock) or record an owner decision. The same question is open for the attempt log in #719.
7. **Which OPTIGA object holds the Infineon certificate is not settled.** This issue and #27 assume `0xE0E0`. The bench chip was recorded with a full device certificate at `0xE0E3` (`secure/src/optiga/mod.rs:2034`). Confirm on a production part before writing the reader. A search of `secure/src` for `E0E0`, `E0C2` and `E0F0` finds no reader today.

Suggested additions to the checklist:

- [ ] Owner decision: may firmware relay a secure-element ECDSA attestation signature that only the host verifies, under invariant 5?
- [ ] Replace the three boot-time boxes with read-and-relay commands plus a host verifier, or record why the on-device ceremony stays.
- [ ] The binding rule and its negative test, in the host verifier.
- [ ] Remove the DHUK probe box. Rewrite the storage boxes against the blank-page rule and the OTP map.
- [ ] Decide the hash.
- [ ] Decide how the identifier readers are gated.
- [ ] Optional, low priority: a serial number of the tamper-evident bag as a manifest field, printed by the host tool. A copy in one-time-programmable memory would need a word from a map that the rollback design and #220 also claim, so it is an owner decision.

What the record does and does not give, so it is not over-claimed later. It answers overbuild by the manufacturer, clone boards without genuine secure elements, a reused identifier and a single swapped chip, and only if the factory record and the log are honest. The release hash inside the manifest is the factory's claim; only the pre-power read (#850) proves what is in flash. A counterfeit board that carries the victim unit's genuine secure elements passes every check on the first day. The research also looked at a per-die attestation key in the microcontroller and concluded that it cannot prove a genuine device on day one under the ship-unlocked model (a fake chip enrols its own key); a post-enrolment variant would be a separate owner decision and is not proposed here.
