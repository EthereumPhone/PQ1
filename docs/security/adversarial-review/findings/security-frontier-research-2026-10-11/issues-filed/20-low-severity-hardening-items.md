TITLE: Low-severity hardening items from the 2026-10 frontier research: no jitter before the first sentinel check, cycle counter exposed to non-secure code, single-read lockout, dead internal tampers, no blank check after erase, placeholder device info
LABELS: finding,priority:low,surface:trustzone,surface:sca-fi,source:frontier-research-2026-10
---
Six small items with no tracking issue. Each is independent; tick them off or split them out as convenient.

Line numbers at master `0feea78a` (2026-10-11). The research ran at `c75b0d9c`, an ancestor of master; the cited files were diffed against master before filing.

- [ ] **No random delay before the first sentinel check after non-secure entry.** `secure/src/nsc/cmd_sign_userop.rs:116`: the first `check_true_into_sentinel` evaluation runs with no jitter after veneer entry and a deterministic LCD status paint, so a glitch can be timed from an observable anchor. Hardening gap, not a bypass (needs two coordinated faults). Fix: one `wait_random` immediately before the first gate of each production veneer, with a source-grep gate.
- [ ] **The debug cycle counter is handed to the non-secure world.** `secure/src/main.rs:4281-4284`. The code never writes `DSCSR`, although its own comment says the CDS bit is needed. A precise cycle counter helps non-secure code time a fault. Whether the counter still counts in Secure state at RDP-2 is not settled.
- [ ] **A single faulted read of the PIN-attempt page ends in a wipe (owner question).** `secure/src/hw/flash.rs:824-833`: `pin_attempts_read` returns the capacity value (32) when its forward and reverse scans disagree. `secure/src/nsc/mod.rs:1450-1458`: a disagreeing pair returns `PinLocked`. The USB arm then wipes (`secure/src/nsc/cmd_request_unlock.rs:118-124`, `:159-164`), and the boot check `pin_attempts_read() >= MAX_ATTEMPTS` (`secure/src/main.rs:1946-1962`) is a single call that also wipes. This is deliberate fail-closed design. The question for the owner: is one transient read fault allowed to destroy a wallet, or should the read be repeated before the verdict? An attacker with the device can already force a wipe with 10 wrong PINs, so this is about accidental loss.
- [ ] **Four internal tampers are enabled but have nothing driving them.** `secure/src/hw/tamp.rs:290` (ITAMP3, the LSE monitor: needs `LSECSSON` and a running 32 kHz crystal; firmware uses neither) and `:293`, `:297`, `:298` (ITAMP7/12/13, the three ADC4 analog watchdogs: no ADC4 driver exists). Correction to the research report, which said these "can never fire": ADC4 is a **non-secure** peripheral here, because GTZC2 is never configured (`secure/src/sau.rs:672-675`), so non-secure code could arm a watchdog and raise these tampers. That is not a new forced-wipe path (`tzic-wipe` already lets non-secure code trigger a wipe by touching a secure peripheral), but the tampers should be either driven from the secure world or not enabled. Option: a small secure ADC4 driver on the internal channels (reference voltage, core voltage, temperature) would make them real monitors with no pin; start log-only.
- [ ] **No blank read-back after the page erase at `FW_BEGIN`.** `secure/src/hw/flash.rs:1307-1352`, `:1366-1386` (`erase_slot`): erase success is judged from the status register only. Later programming is read-back verified, so a missed erase matters only for bytes that are never written, which is the unmeasured slot tail ({{22}}).
- [ ] **`GET_DEVICE_INFO` returns placeholders.** `nonsecure/src/usb/commands.rs:182` (`FW_VERSION = [0x03, 0x00, 0x00]`), `:416` (16 zero bytes for the device UID), `nonsecure/src/usb/mod.rs:200` (serial "0001"). The source comment already calls this a hardcoded placeholder. It needs replacing before a companion relies on it.

Evidence level for all six: code read, re-checked independently at `c75b0d9c`. Nothing measured on silicon.

Two rows of the report were **dropped** on that re-check and are not filed: the claim that a brown-out reset skips a needed scrub (the runtime already clears `.bss` and `.data` on every reset, and no static escapes that), and the claim that `wait_random` uses a constant before the RNG is initialised (no caller runs that early).
